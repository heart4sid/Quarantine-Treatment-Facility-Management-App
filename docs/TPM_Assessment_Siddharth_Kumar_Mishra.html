Question 03 / 04
Logical Constraints for Developers
Additional logical constraints not immediately apparent from screen designs - when to show warnings, edge cases, business rules, and system behaviors.
⚠️
These constraints represent the hidden complexity that separates a working prototype from a clinically safe production system. Each item below would be invisible from UI wireframes alone but is critical to implement correctly.
1
Temperature Entry: Append-Only, Never Overwrite
If a nurse logs a second temperature for the same patient on the same calendar day, the system must warn ("Already logged today - confirm re-entry?") and append the new entry to the audit trail - never silently overwrite the original. Clinical calculations (fever streak) use the latest reading of the day, but the full entry history is retained for audit integrity. Silent overwrite is a patient-safety failure.
Patient SafetyData Integrity
2
Fever Streak Reset: Any Single Fever Reading Resets the Counter
Even if a patient has earlier normal readings on the same calendar day, a single fever reading (100.4F / 38C) resets the discharge-eligibility streak to 0. Patient safety takes precedence over convenience. Do not average daily readings; use the worst reading per day for streak logic. A doctor reviewing a 2-day streak must be certain those 2 days had no fever reading at all.
Patient Safety
3
"Day" is Calendar Day (Midnight Boundary), Not Rolling 24 Hours
A nurse's "measured today" status resets at 00:00 facility local time, not 24 hours after the last log. Critical for shift handover clarity: logging at 23:55 and at 00:05 next day are valid for their respective dates. The "3-day streak" for discharge eligibility counts 3 consecutive calendar days, not 72 hours. Build time zone handling explicitly - never rely on server UTC with no offset.
Business LogicUX
4
Doctor-Before-Nurse Visit: Warn and Log Exception, Do Not Hard-Block
If a doctor attempts to visit a patient with no temperature recorded today, show warning: "No temperature recorded today - recommend nurse measurement first." However, the system must allow the doctor to proceed (clinical urgency exists), but must require a mandatory reason field and log this as an exception in the audit trail. Hard-blocking creates dangerous workarounds such as fake temperature entries.
Patient SafetyAudit
5
Discharge Requires Explicit Doctor Sign-Off - Never Auto-Discharge
The system auto-flags a patient as "Discharge Eligible" after 3 consecutive fever-free calendar days, but must never execute the discharge automatically. The doctor must actively confirm, because clinical edge cases exist: relapse risk, pending lab results, transport readiness. Once the doctor approves, the discharge moves to Admin queue for execution. A 2-step (doctor approves then admin executes) workflow is mandatory, not a simplification.
Patient SafetyWorkflow
6
Bed Capacity Hard Cap: 74 Beds - No Silent Overbooking
At 74/74 occupied beds, the admission form must hard-block new admissions with a clear error message and offer a waitlist option. The capacity check must be a server-side atomic transaction - not just a client-side UI check - to prevent a race condition where two simultaneous admissions both see "73/74" and both succeed, resulting in 75 occupied beds. Use a database-level lock or optimistic concurrency check.
Business LogicConcurrency
7
Role-Based Write Restrictions: Enforced Server-Side, Not UI-Only
A nurse must not be able to approve a discharge by calling the API directly, bypassing the UI. A doctor must not be able to log a temperature. Admin must not be able to alter clinical data. These restrictions must be validated in every API route/server action handler, not just hidden from the UI. Every mutation endpoint must verify the session user's role before executing any database write.
SecurityCompliance
8
Mortality Rate Calculation: Exclude Currently-Admitted Patients
Facility mortality rate = deceased / (discharged + deceased). Patients still admitted are excluded from both numerator and denominator. This is clinically correct - admitted patients have unknown outcomes. Alert thresholds (mortality >15%) should use a rolling window (e.g., last 30 days or last 20 completed cases) to avoid false alarms from statistical noise with small sample sizes.
Business LogicQuality Monitoring
9
Data Correction: Amend, Do Not Delete - Require Reason Code
Any correction to a logged temperature or outcome must create an amendment record rather than silently updating the original. The amendment must capture: original value, corrected value, timestamp, correcting user, and a mandatory reason code. No hard deletes of clinical data should ever be possible - this is a compliance requirement equivalent to HIPAA audit integrity standards.
Data IntegrityCompliance
10
Offline Resilience: Queue Locally, Sync on Reconnect
Clinical settings often have poor connectivity. Nurse temperature logging and doctor visit notes should queue locally (IndexedDB / service worker) if the network is unavailable and sync when connectivity is restored. The UI must clearly indicate "offline mode - will sync." Synced entries must carry the original timestamp of the local entry, not the sync time - otherwise the audit trail is misleading.
UXData Integrity
11
Fever Threshold: Configurable, Not Hard-Coded
The fever detection threshold (100.4F / 38C) must be stored as a facility-level configuration value in the database, not hard-coded in application logic. Facility policies may differ (some use 37.5C), and the value may need updating without a code deployment. All historical temperature classifications should be recalculated when the threshold changes, or at minimum a warning shown that historical flags used the old threshold.
Business LogicConfiguration
12
Waitlist Auto-Promotion: FIFO with Notification, Not Silent
When a bed is freed by a discharge, the system should not auto-admit the next waitlist patient (clinical assessment may still be needed). Instead, it should surface the next waitlist patient to Admin with a notification/queue prompt: "Bed available - [Patient Name] is next in queue (waiting X hours)." FIFO ordering is required unless the Admin manually re-prioritizes with a logged reason.
Business LogicUX

Question 04 / 04
Sprint Planning & Knapsack Optimization
In the next sprint planning meeting, velocity is 25 SP. You already plan to finish 3 stories of 5 points each (15 SP committed). Which features (A through J) to add such that effort is minimized and value is maximized? (High = 2X Medium, Medium = 3X Low).
📐
Mathematical Formulation: Total Velocity = 25 SP | Committed = 15 SP (3 x 5) | Available Capacity = 10.0 SP
Value Weights: Low = 1 pt | Medium = 3 pts (3X Low) | High = 6 pts (2X Medium)
Objective: Maximize total value V while strictly minimizing effort E subject to E ≤ 10.0 SP.

💡
TPM Trade-Off Rationale: Why Defer Feature C to the Following Sprint?
Feature C (High Priority, 5.0 SP, Value = 6) has an ROI of 1.20. Taking Feature C consumes 50% of the entire available sprint capacity. By swapping C for the package of {D, G, H, I, J} (Effort = 3.3 SP, Value = 7), the team achieves HIGHER value (+1 point) for 1.7 SP LESS effort! In agile terms, Feature C represents an epic that should be groomed and decomposed into smaller user stories prior to sprint ingestion.
