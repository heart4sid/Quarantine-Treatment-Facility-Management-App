0. Read this first: what "free on Vercel" can and cannot carry

The architecture in this document is designed to run on free tiers. But three findings from the Vercel/Neon terms materially change how the free tier should be used for a clinical system. Decide on these before writing code.

# Finding Implication
F1 Vercel's Hobby plan is restricted to non-commercial, personal use (Vercel Hobby docs). A system that runs a live treatment facility is unlikely to fit that definition. Treat Hobby as fine for development, staging, demos, and a pilot with synthetic data. Check Vercel's fair-use guidelines for your specific organization (e.g., non-profit/government) before going live.
F2 No HIPAA BAA on Hobby. The BAA is a paid add-on for Pro (listed at $350/month) or available on Enterprise (Vercel HIPAA guide). Neon's free plan is similarly a dev/side-project tier. Do not store real patient data on free tiers where HIPAA or an equivalent health-data law applies. The PRDs require PHI-equivalent protection (v1 §6, v2 §6), and a legal/compliance review must confirm what your jurisdiction demands.
F3 Hobby has no uptime SLA and, per third-party summaries of Vercel's behavior, a project that exceeds a Hobby limit is paused rather than billed — an outage, not an overage (summary). The PRD's 99.9% uptime target cannot be guaranteed on free tiers. This TRD compensates with offline-first clients, a degraded read-only mode, and a paper-fallback runbook (§13).

How this TRD handles it — a two-stage plan:

  • Stage 0 (free, $0): Everything in this document runs on Vercel Hobby + Neon Free + free monitoring. Use it for build-out, UAT, staff training, and demos with synthetic data only.
  • Stage 1 (production, minimum paid): Same codebase, no re-architecture. Move to Vercel Pro (+ BAA if required), and Neon Launch (roughly $19/month for an always-on 0.25 CU compute — see §14). §15 lists exact "graduation triggers".

Portability rule (non-negotiable): Use only portable building blocks — Next.js, standard Postgres, standard HTTP endpoints. Anything Vercel-specific (Vercel Cron, Vercel Blob/KV) is wrapped behind a thin adapter so the app can move to a container host or VPS without rewrites.

5. Data model

5.1 Global conventions

  • Primary keys: UUIDv7 (time-ordered; also generated client-side for offline records).
  • Every tenant table has facility_id uuid NOT NULL.
  • Timestamps: timestamptz, UTC. Display and day-boundary logic use facilities.timezone (IANA).
  • No hard deletes anywhere. Clinical tables are append-only (§5.4). Non-clinical tables use deactivated_at.
  • Temperature stored in °C canonically; display unit is a facility setting.
  • PII fields (patient name, phone, email, address) are application-layer encrypted (AES-256-GCM, key in encrypted env var) with a keyed hash "blind index" where equality lookup is needed.

5.4 Invariants enforced in the database (not just in code)

-- 1. One open admission per bed  => hard guarantee against overbooking (V1 §5.6)
CREATE UNIQUE INDEX one_open_admission_per_bed
  ON admissions (bed_id) WHERE closed_at IS NULL;

-- 2. One open admission per patient
CREATE UNIQUE INDEX one_open_admission_per_patient
  ON admissions (patient_id) WHERE closed_at IS NULL;

-- 3. Idempotent offline sync
CREATE UNIQUE INDEX uq_temp_client_uuid ON temperature_readings (client_uuid);

-- 4. Append-only clinical tables
CREATE FUNCTION forbid_mutation() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN RAISE EXCEPTION '% is append-only', TG_TABLE_NAME; END $$;

CREATE TRIGGER temperature_readings_immutable
  BEFORE UPDATE OR DELETE ON temperature_readings
  FOR EACH ROW EXECUTE FUNCTION forbid_mutation();
-- (repeat for visits, discharge_*, audit_log, med_administrations, lab_results)

-- 5. Least privilege: the app's DB role cannot rewrite history
REVOKE UPDATE, DELETE, TRUNCATE ON temperature_readings, visits, audit_log FROM app_role;

admissions has a small set of legitimately mutable columns (discharge_eligible_since, closed_at, outcome, bed_id on transfer). These are updated through a single service function, each change writing an audit_log row in the same transaction.

6. Core domain logic

6.1 Facility-local "day"

local_date = (recorded_at AT TIME ZONE facilities.timezone)::date, computed once at insert and stored. All "today" queries use local_date, never a rolling 24 h window (V1 §5.4). Facility timezone changes are prohibited after go-live (would corrupt local_date history) — admin change requires a migration script.

6.2 Fever-free streak and discharge eligibility (V1 §4.3, §5.3)

The streak is derived, never stored. The DB returns per-day facts; a pure function computes the result.

// /domain/streak.ts
export type DayFact = { date: string /* YYYY-MM-DD, facility-local */; anyFever: boolean };

export function computeStreak(days: DayFact[], today: string): number {
  // days: one entry per local_date that has >=1 effective reading, sorted ascending.
  const byDate = new Map(days.map(d => [d.date, d.anyFever]));
  let streak = 0;
  for (let d = today; ; d = prevDate(d)) {
    const fever = byDate.get(d);
    if (fever === undefined) {
      // Today not yet measured is neutral; an unmeasured PAST day breaks the streak.
      if (d === today) continue;
      break;
    }
    if (fever) break;
    streak++;
  }
  return streak;
}
export const isDischargeEligible = (streak: number, n: number) => streak >= n;

-- Per-day facts for one admission (input to computeStreak)
SELECT local_date AS date, bool_or(is_fever) AS any_fever
FROM effective_temperature_readings
WHERE admission_id = $1
GROUP BY local_date
ORDER BY local_date;

Rules encoded (see §17 G1–G2 for the PRD ambiguities they resolve):

  1. A day is a fever day if any effective reading that day is a fever (safety-first, V1 §5.3). Erroneous readings are removed via amendment, not by re-entering a "better" value.
  2. A day with no effective reading breaks the streak (except today before measurement).
  3. Eligibility = streak ≥ facility.discharge_streak_days (default 3).
  4. Edge-triggered event: on every temperature write/amendment, the service recomputes eligibility inside the transaction. On transition not eligible → eligible it sets admissions.discharge_eligible_since and emits patient.discharge_eligible. On eligible → not eligible it clears the flag and voids any un-executed approval (§6.3).
  5. Property-based tests (fast-check) must cover: date gaps, DST changes, amendments, multiple same-day readings, midnight-boundary timestamps, and threshold changes mid-stay (threshold is snapshotted per reading).

6.3 Discharge lifecycle (V1 §4.4, §5.5)

stateDiagram-v2
  [*] --> Admitted
  Admitted --> DischargeEligible: streak >= N (derived, edge event)
  DischargeEligible --> Admitted: fever logged / reading amended
  DischargeEligible --> ApprovedForDischarge: doctor approves
  ApprovedForDischarge --> Admitted: fever logged before execution (approval voided)
  ApprovedForDischarge --> Discharged: admin executes (eligibility re-validated)
  Admitted --> Deceased: doctor records outcome
  Admitted --> Transferred: doctor records outcome
  Discharged --> [*]
  Deceased --> [*]
  Transferred --> [*]
  • Approval requires role doctor and current eligibility. Execution requires role admin_staff, a non-voided approval, and re-validated eligibility inside the same transaction; on failure the API returns 409 ELIGIBILITY_CHANGED and the UI asks the doctor to re-review.
  • Execution transaction: insert discharge_executions, set closed_at and outcome = DISCHARGED_CURED, free the bed (implicit: the partial unique index stops counting a closed admission), write audit_log, enqueue notifications.
  • No auto-discharge under any condition.

6.4 Admission, capacity and waitlist (V1 §4.1, §5.6)

-- Inside a transaction: claim a free bed atomically
SELECT b.id
FROM beds b
WHERE b.ward_id = $1 AND b.is_active
  AND NOT EXISTS (SELECT 1 FROM admissions a WHERE a.bed_id = b.id AND a.closed_at IS NULL)
ORDER BY b.label
FOR UPDATE SKIP LOCKED
LIMIT 1;
  • Row returned → insert admission (unique index is the final guard against races).
  • No row → return 409 AT_CAPACITY and create a waitlist_entries row. The UI shows the waitlist.
  • When a bed frees up, emit bed.available to Admin (v2a) with the next waitlisted entry.
  • Occupancy alerts (V2 §4.1, ≥90%) are evaluated on every admit and discharge (event-driven, no scheduler needed).

6.5 Doctor visit ordering (V1 §4.3, §5.2)

  • Starting a visit when no effective reading exists for local_date = today returns 428 TEMP_MISSING_TODAY with a warning payload.
  • The client may retry with { proceedAnyway: true, exceptionReason: "..." } (non-empty, min length enforced). Stored as visits.no_temp_exception = true.
  • Exception counts feed the Facility Head dashboard.

6.6 Duplicate temperature entries (V1 §4.2, §5.1)

  • Second entry on the same local_date: API returns 409 DUPLICATE_TODAY with the existing reading; client asks "already logged — confirm re-entry?"; on confirm it re-sends with confirmDuplicate: true.
  • Both rows are retained. Because any fever reading makes the day a fever day (§6.2), a duplicate can never hide a fever.
  • Nurses can amend only their own same-day readings; doctors can amend any reading; all amendments require a reason code (§17 G10).

6.7 Mortality (V1 §4.5, §5.8)

mortality_rate = DECEASED / (DISCHARGED_CURED + DECEASED)      // TRANSFERRED excluded; open admissions excluded
  • Computed over a rolling window (7 and 30 days, configurable) and lifetime.
  • Alert fires only when (cured + deceased) >= mortality_alert_min_sample and rate > threshold — avoids small-sample noise. Optionally use a Wilson lower bound instead of the point estimate.
  • Alert is edge-triggered with hysteresis (re-arms after the rate falls below threshold − 2 pts) to prevent alert spam.
  • Dashboard shows rate against the 85% survival benchmark.

6.8 Amendments and corrections (V1 §5.9)

Correction = new row with amends_id, reason_code (enum + optional free text), acting user. Outcome corrections follow the same pattern via an admission_outcome_amendments table. Streak and mortality recompute automatically because they derive from effective rows; recomputation may flip eligibility, handled by §6.2 rule 4.

7. Security, authentication and authorization

7.1 Authentication

  • Email + password (Argon2id) or passkeys; TOTP MFA required for doctor, admin_staff, facility_head, system_admin, regional_admin.
  • Shared bedside tablets (V1 §6 usability): fast user switching via short PIN after an initial full login on the device; 5-minute idle lock; every write is attributed to the currently unlocked user, never the device. PIN attempts rate-limited and lock after 5 failures.
  • Sessions: HttpOnly, Secure, SameSite=Lax cookies; server-side session records (revocable by System Admin).

7.3 Tenant isolation via Postgres RLS (V2 §5.3)

ALTER TABLE admissions ENABLE ROW LEVEL SECURITY;
ALTER TABLE admissions FORCE ROW LEVEL SECURITY;

CREATE POLICY facility_isolation ON admissions
  USING (facility_id = ANY (string_to_array(current_setting('app.facility_ids', true), ',')::uuid[]));
-- Repeat for every tenant table.

Every request runs in a transaction that begins with:

SELECT set_config('app.user_id',      $1, true),   -- true = transaction-local (safe with pooled connections)
       set_config('app.facility_ids', $2, true),
       set_config('app.role',         $3, true);
  • The application DB role must not own the tables and must not have BYPASSRLS.
  • Regional Admin has no policy on patient-level tables at all. They read only daily_facility_metrics (aggregates). Isolation is structural, not a UI choice.
  • v1 ships with RLS enabled and a single facility. v2c then only adds scopes and the Regional role.
  • Mandatory automated test: for every tenant table, a user scoped to Facility A gets zero rows for Facility B, including through joins, views, and export endpoints.

7.4 Data protection

  • TLS everywhere (Vercel default); DB provider encrypts at rest.
  • Field-level encryption for direct identifiers (§5.1); keys in Vercel encrypted env vars; key rotation via versioned key IDs stored alongside ciphertext.
  • No PHI in: URLs, push payloads, email subjects, logs, Sentry events (scrub beforeSend), analytics.
  • Patient-level read access is written to access_log.
  • Security headers: strict CSP, HSTS, X-Frame-Options: DENY, Referrer-Policy: no-referrer.

7.5 Abuse protection

  • Rate limits per IP and per user on auth, PIN, family-link and integration endpoints.
  • Cron/tick endpoints require Authorization: Bearer $CRON_SECRET (constant-time compare).
  • Lab integration endpoints use per-source API keys (stored hashed), optional HMAC request signature, and payload size cap.

7.6 Compliance

  • Design to least-privilege, audit logging, retention policy (V1 §6). Retention period is an open question (V1 §8.4); the schema supports retention via archival flags, never deletion.
  • Legal review must confirm applicable regime and whether free tiers are acceptable (see F1–F2).

8. API design

8.1 Conventions

  • Base path /api/v1; JSON; Zod-validated; errors as RFC 9457 problem+json with stable code.
  • Idempotency: all mutating clinical endpoints accept client_uuid (or Idempotency-Key header); replays return the original result.
  • Optimistic concurrency where mutable (admissions) via version column / If-Match.
  • Cursor pagination; list endpoints default page size 50.
  • Polling endpoints return ETag; clients send If-None-Match and receive 304 cheaply.

8.3 Performance approach (V1 §6: <2 s at 74 patients)

  • Indexes: (facility_id, admission_id, local_date) on readings; partial index on open admissions; (facility_id, closed_at).
  • Task-list queries use a LEFT JOIN LATERAL for "latest effective reading today" — one query per list.
  • Same-region Vercel + Neon; pooled connection; RSC streaming for dashboards.
  • Budget: p95 API ≤ 400 ms warm; page load ≤ 2 s including a Neon cold resume (documented as a few hundred ms).

9. Offline-first client (V1 §5.10)

Scope: logging temperatures, starting visits/notes, and medication administration (v2b) must work offline. Admissions, discharge execution, and analytics are online-only.

Mechanism

  1. Service worker precaches the app shell and the user's task list; stale-while-revalidate for reads.
  2. Writes go to an IndexedDB outbox with a client-generated UUIDv7 (client_uuid) and client_recorded_at.
  3. Background Sync (where supported) plus a foreground retry loop flush the outbox via POST /sync in order.
  4. Server processes each item independently and idempotently; response lists per-item results (created / duplicate / rejected+reason).
  5. UI shows a persistent sync badge ("3 pending") and never claims a record is saved until the server confirmed it — offline items are visibly "pending".

Conflict and integrity rules

  • Offline duplicates for the same day are both stored (append-only). The advisory "already logged" prompt is best-effort offline.
  • local_date is derived from client_recorded_at only if within an accepted skew of server receipt (default: not in the future, not older than 72 h); otherwise the server flags the row clock_suspect = true and uses server time. Skew above 5 minutes is logged per device.
  • Discharge-eligibility events fire when the server processes the write, so delayed sync delays notifications — the UI shows "last synced" prominently so staff know how fresh their view is.
  • Outbox is encrypted at rest on the device (Web Crypto, key derived from session) and purged on logout after confirmed sync. Logout with unsynced items requires explicit confirmation.

10. Notifications, alerts and scheduling (V2 §4.1, §5.1)

10.1 Event-driven first

Most alerts don't need a scheduler; they are emitted inside the write transaction that causes them:

Event Emitted by Recipient
patient.discharge_eligible temperature write (§6.2) Assigned doctor
discharge.approved approval Admin queue
bed.available discharge/transfer Admin
occupancy.near_capacity (≥90%) admit/discharge Facility Head
mortality.threshold_breached outcome write Facility Head
lab.unmatched lab ingestion Admin/Doctor

10.2 Guaranteed in-app record; push is a doorbell

  • In the same transaction as the event, insert a notifications (in-app inbox) row and a notification_outbox row per channel. → A clinical alert can never be silently dropped (V2 §5.1).
  • Delivery: attempted immediately after commit (Next.js after()/waitUntil), retried by the tick job with exponential backoff (attempts, next_attempt_at).
  • Critical alerts (discharge_eligible, mortality) require acknowledgment; unacknowledged after N minutes → escalate to a secondary recipient (Doctor→Admin, Facility Head→System Admin).
  • Coalescing / rate limiting: dedupe_key (e.g., event:admission_id) prevents duplicates; bursts collapse into a digest ("4 patients discharge-eligible").
  • Quiet hours (per-user prefs) suppress push/SMS for non-critical events; critical events still go in-app and to on-duty staff (design decision — see §17 G11).
  • No PHI in payloads: push text like "1 new discharge-eligible patient — open app" (no name, no bed).

Free-tier scheduler options for the 5–15 min tick: a free external cron service (e.g., cron-job.org), Upstash QStash free tier, or GitHub Actions schedule. Notes: GitHub-scheduled runs can be delayed and free private-repo minutes are limited (a 10-minute cadence would use ~4,300 minutes/month, above the 2,000 free minutes for private repos — verify current limits). Recommended: two independent schedulers for redundancy; the endpoint is idempotent and protected by a Postgres advisory lock so overlapping ticks do nothing harmful. The ping carries no PHI, so a third-party scheduler is acceptable.

vercel.json (daily only — Hobby rejects more frequent schedules at deploy time):

{

    { "path": "/api/v1/cron/daily", "schedule": "0 22 * * *" }

}

Schedules are UTC with hour-level precision; choose a time that always lands after facility-local midnight, and make the job safe to run late.

11. v2 module designs

11.1 Treatment & medication (V2 §4.2, v2b)

Table Notes
treatment_plans admission_id, doctor_id, status, version, supersedes_id
medication_orders plan_id, drug_name, optional code (RxNorm/ATC), dose, unit, route, frequency_spec (structured: interval or fixed times), start_at, end_at, status (PENDING_VERIFICATION→ACTIVE→STOPPED), verified_by
med_slots Materialized expected administrations: order_id, due_at, window_end
med_administrations slot_id, status (ADMINISTERED/MISSED/REFUSED), by_user, at, note, client_uuid — append-only
  • Orders are versioned, not edited: changing a dose creates a new order superseding the old one; future slots of the old order are cancelled by a new row, not deleted.
  • Slot generation: on activation, generate slots for a 72-hour rolling horizon; the daily job extends it. (72 h means a missed daily cron can't starve nurses.)
  • Overdue is derived (now > window_end AND no administration). The sweep emits alerts; nurses record MISSED explicitly, or a system actor records it after a configurable grace period.
  • Conflicts: on slot generation, detect overlapping windows for the same patient and attach a conflict_flag for doctor review. Flag only — never block or auto-resolve (V2 §5.2).
  • Pharmacist verification is a facility setting; if on, slots aren't generated until ACTIVE.
  • Treatment history remains queryable on any later admission via patient_id (V2 §4.2).
  • No drug-interaction checking (out of scope).

11.2 Multi-facility & Regional Admin (V2 §4.3, v2c)

  • Because v1 already has facility_id + RLS, v2c adds: networks, user_facility_scopes with >1 rows, the regional_admin role, ward-level filters in UI, and daily_facility_metrics.
  • Capacity is per facility/ward and enforced by bed rows + the unique index — a Regional Admin has no write path to beds, so cannot override limits (V2 §5.7).
  • Migration from v1 is additive: existing rows already carry the default facility_id. Expand/contract migrations only (§16).

11.3 Family status view (V2 §4.4, v2d)

Table Notes
family_contacts patient_id, contact_enc, channel, consent_at, consent_by (patient/guardian + recorder), consent_evidence_ref, revoked_at
family_links token_hash (SHA-256), expires_at, revoked_at, last_viewed_at
  • Token: 256-bit random, shown once, only the hash is stored. URL /s/{token} contains no identifiers.
  • Consent gate: links cannot be created unless consent_at is set. Admin can revoke instantly; revocation is checked on every request.
  • Expiry: default admission + 60 days or discharge + 7 days, whichever is earlier (configurable).
  • Response contains only: admission date and one of ADMITTED, UNDER_OBSERVATION, DISCHARGE_ELIGIBLE, DISCHARGED. No temperatures, notes, treatment, diagnosis, or bed number.
  • Headers: Cache-Control: no-store, X-Robots-Tag: noindex, Referrer-Policy: no-referrer; rate-limited per IP; identical response for invalid/expired/revoked tokens.
  • Deceased or transferred outcomes must never auto-update the family link or auto-send a notice. The page shows a neutral "Please contact the facility" message and notification is a human process (§17 G4).
  • Automated discharge notification goes out via email (free) or SMS (paid adapter) on discharge execution.

11.4 Analytics & reporting (V2 §4.5)

  • Pre-aggregation: daily_facility_metrics(facility_id, date, admissions, discharges, deaths, transfers, occupied_eod, sum_los_hours, …). Nightly job finalizes the previous day; "today" is computed incrementally on write. Dashboards read only rollups.
  • Readmission: at admission time, look up prior closed admissions by patients.identity_hash within readmission_window_days; set admissions.readmission_of. If no strong identifier exists, create a possible_duplicate_of suggestion for manual confirmation rather than auto-matching (avoids false positives — V2 §5.5).
  • Cohorts: group by ISO admission week; outcomes and LOS per cohort; annotate protocol-change dates.
  • Workload views: tasks completed per shift, framed as capacity. Individual-level views gated by an open product decision (V2 §8.4); default is management-only aggregates by shift.
  • Exports: CSV streamed from a route; PDF via pdf-lib. Exports are audited and RLS-scoped. Regulatory exports contain aggregates only unless explicitly authorized.
  • Same-day anomaly alerting (V2 §2): the mortality and readmission-rate checks run on write and in the tick.

11.5 Lab & external integration (V2 §4.6)

  • POST /integrations/labs/fhir accepts FHIR R4 Bundles (Observation, DiagnosticReport). Auth via per-source API key + optional HMAC signature.
  • Mapping: resolve patient via Patient.identifier → patients.mrn/identity_hash. Unmatched or ambiguous results go to lab_results_inbox (PENDING_REVIEW) for Admin/Doctor reconciliation — never discarded, never guessed (V2 §5.6).
  • Idempotency on (source_id, external_id); corrected results arrive as new versions; lab_results is append-only.
  • Manual entry remains the fallback (same table, source = 'manual').
  • Limitation: Vercel cannot receive raw TCP (HL7 v2 over MLLP). Labs that only speak HL7 v2 need a small bridge on their side, or an interface engine, that converts to HTTPS/FHIR. Confirm the lab's actual capabilities (V2 §8.3) before committing to this phase.

13. Reliability, observability and recovery

13.1 Degraded modes

  1. App/DB unreachable: clients continue from cache and outbox (temps, visits, doses); a banner shows offline state.
  2. DB quota exhausted / paused: read-only static "downtime sheet" page (pre-rendered list of current patients/beds/tasks, refreshed at each successful poll and stored client-side) so staff can continue on paper and back-enter later.
  3. Full outage: printed downtime procedure (paper temp log template, back-entry procedure, who to call). Ship this as a deliverable, not an afterthought.

13.2 Monitoring

  • Sentry (errors, PII scrubbed), uptime pinger against a DB-free /api/health and a deeper /api/health/deep checked at low frequency (so monitoring doesn't burn Neon compute hours).
  • Business monitors (in the tick job): "no temperature logged for >X% of patients by cutoff", "outbox sync failures", "notification failures", "cron heartbeat stale" → alert to System Admin. A missing heartbeat is itself an alert.

13.3 Data integrity checks (nightly)

Orphaned admissions, beds with >1 open admission (should be impossible), readings with clock_suspect, eligibility flags inconsistent with recomputation.

13.4 Backup & DR

  • Free-plan point-in-time restore windows are short; do not rely on them.
  • Nightly pg_dump (schema + data) → encrypted (age/GPG) → off-platform object storage (e.g., a free-tier bucket such as Cloudflare R2 — verify quota and terms). Keep 30 daily + 12 monthly copies.
  • Monthly restore drill into a Neon branch, verified by row counts and invariant checks.
  • Targets (Stage 0, best-effort): RPO ≤ 24 h, RTO ≤ 4 h. Stage 1 targets are tightened with paid PITR.

14. Free-tier capacity budget

Assumptions: 74 beds, ~40 staff accounts, ~25 concurrent users at peak.

Resource Estimate Free limit Verdict
Rows written/day ~74 temps (×1–2) + 74 visits + ~300 med admins (v2) + audit ≈ 1,000–1,500 — —
DB storage/year ~0.4M rows × ~0.3 KB incl. indexes ≈ 100–200 MB 0.5 GB (Neon Free) ✅ ~1–2 years incl. v2; monitor
Function invocations/month ~40 users × ~300 req/day × 30 ≈ 360k (+ ticks ~9k) ~1M reported ✅ but polling can inflate — see below
Bandwidth JSON + cached shell, well under a few GB ~100 GB reported ✅
Neon compute Compute stays awake 5 min after each query. Active 16 h/day ≈ 480 h × 0.25 CU = ~120 CU-h/month 100 CU-h/month ⚠️ Likely exceeded in real 24×7 operation

Polling can silently multiply invocations and keep the DB awake. Mitigations:

  • Poll only while the tab is visible; back off to 2–5 min when hidden; use ETag/304 responses served without touching the DB when nothing changed (a lightweight events_cursor in a cache or edge-cacheable response).
  • Batch offline sync instead of per-record calls.
  • Hit the DB-free health route from uptime monitors.

Even so, plan for compute to be the first free limit that binds. Always-on 0.25 CU on Neon's Launch plan is ≈ 0.25 × 730 h × $0.106 ≈ $19/month at published 2026 rates (Neon pricing) — small, and it also removes cold starts and free-plan hard stops. A Neon Free project that exhausts hours suspends compute until the next billing period (Neon FAQ) — an outage; therefore set a usage alert at 70% of quota.

17. PRD ambiguities found and technical decisions taken

These need product/clinical confirmation but are resolved conservatively so engineering isn't blocked.

ID Gap in PRD Decision in this TRD
G1 V1 §4.2 says the "latest value" of the day is used for calculations; V1 §5.3 says any fever reading that day resets the streak. These conflict. Any effective fever reading makes the day a fever day (safety-first). Wrong readings are removed by amendment.
G2 "3 consecutive fever-free days" doesn't say what happens when a day is unmeasured (V1 §8.2 also leaves calendar-vs-72h open). Calendar days; an unmeasured past day breaks the streak. streak_mode reserved for a future rolling-72h option.
G3 What if a fever is logged after doctor approval but before admin executes? Approval is voided automatically; execution returns 409; doctor must re-approve (§6.3).
G4 v2 family statuses don't cover death/transfer. Never automated. Neutral message + human notification (§11.3).
G5 V1 §4.5 lets "admin/clinical staff" log outcomes, but §3 says admin can't enter clinical data. DECEASED/TRANSFERRED = doctor only. Admin executes only cured discharge logistics.
G6 "Assigned patients" and "per shift" metrics need an assignment/shift model that isn't defined. Added shifts + patient_assignments (§5.3). Assignment UI is an Admin function.
G7 Waitlist ordering and bed-freed behavior are undefined. FIFO with optional priority; bed.available notifies Admin; admission remains a manual Admin action.
G8 v1 lists multi-facility as a non-goal, but v2 needs it. v1 schema carries facility_id and RLS from day one (small cost, avoids a risky migration).
G9 Mortality alert threshold equals the expected 15% rate; noisy at small n. Min-sample gate + hysteresis (§6.7).
G10 V1 §3 lets nurses edit "own same-day" entries, while §5.9 requires reason codes for all corrections. Both apply: nurse amendments are same-day/own-only and need a reason; later corrections are doctor-only.
G11 Quiet hours vs. critical alerts. Quiet hours suppress push/SMS for non-critical only; critical still lands in-app and to on-duty staff.
